# Восстановленная прошивка XIAO

29 октября 2026. После восстановления приложения из APK восстановлена собираемая UDP-прошивка XIAO. [Исходники сохранены в RC_CAR_ESP32, ветка restore-udp](https://github.com/BlowYourBrain/RC_CAR_ESP32/tree/restore-udp). Сохранившиеся19 файлов C++ проверены по хешам; UDP-ядро и основной цикл написаны заново по контракту клиента. Это совместимая реконструкция, а не точный исходный текст утраченной программы.

Штатные сборки для домашней Wi-Fi-сети и отдельной стендовой AP используют `backend=null`: GPIO мотора и серво не инициализируются. Сохраняются полный ID платы, один владелец IP/порт/attempt/token, явный ARM с нулевыми осями,200мс свежести клиента и250мс сторожевого таймера платы. Повторные пакеты и старый ACK-базис не продлевают сеанс бесконечно. Сторожевой поток работает независимо от сетевого цикла, под общим mutex с состоянием управления.

## Что проверено

- Нативное C++-ядро: формат пакета, неверные входы/владелец/ID, повторы, истечение перед обработкой, неудачная отправка ACK, переполнение времени/sequence, STOP, быстрый STOP→новый ARM и первая нулевая выборка привода.
- Настоящий Kotlin `UdpControlClient` и C++-ядро через UDP-сокеты на ПК: прямой/обратный ход, второй клиент, принятый STOP, потеря всех пакетов, остановка по сроку и новое нейтральное подключение.
- Обе штатные прошивки скомпонованы для ESP32-S3; в ELF отсутствуют определённые символы физических драйверов. Включение привода без калибровки отвергается целевым компилятором. Отдельный синтетический образ скомпонован только для проверки связи модулей и не загружался.
- Реальная плата идентифицирована перед загрузкой; свежие8МБ flash прочитаны и сверены. Записан только app0 по адресу0x10000, затем выполнена отдельная проверка digest. Загрузчик, разделы и NVS сохранены. Плата загрузилась, подключилась к Wi-Fi и сообщила `outputsEnabled=false`, `actuatorMode=disabled`, правильный полный ID и отключённое энергосбережение Wi-Fi.

Настоящий Kotlin-клиент также проверен с ПК через Wi-Fi реальной XIAO: поиск v2/ID/занятость, защита владельца, удержание команд вперёд и назад, нейтраль после закрытия клиента и при молчании. Длительности, RTT, итоговый JUnit и хеши находятся в [отчёте](evidence/firmware-udp-2026-10-29/summary.json). На устройстве нейтраль после закрытия не отличает доставленный STOP от истечения таймера; принятый STOP отдельно подтверждён нативным межъязыковым тестом. Проверка не измеряет физическое время остановки колёс.

Samsung сейчас отсутствует в ADB. Его прежние успешные прогоны относятся к оригинальной прошивке; новая прошивка ещё не проверена через экран телефона. APK и данные приложений в этом этапе не менялись.

**Ограничение устойчивости:** первый отдельный60с прогон прошёл с максимальным RTT47мс, но повтор в общем наборе оборвался через11,793с с `ACK freshness timeout`; итоговая нейтраль платы проверена. Следующий отдельный60с прогон с диагностикой прошёл с RTT25мс. Причина единичного обрыва не установлена: успешные проходы его не отменяют. Сроки200/250мс не изменены. Для проверки через телефон нужен снова подключённый Samsung; до выяснения устойчивости и проверки питания аппаратный привод не включать.

Финальный общий прогон прошёл:61 тест,60 успешных и один пропущенный условный WebSocket fleet-тест. В нём выполнены новый нативный UDP interop и ещё один60с прогон реальной платы с RTT37мс. Все три успешных аппаратных прогона и неудачный повтор сохранены в отчёте.

## Воспроизведение

См. README firmware-репозитория для сборки/нативных проверок. Из Android-репозитория, с настроенными JAVA_HOME и ANDROID_HOME:

```powershell
uv run --no-project --python 3.12 --with ziglang==0.14.1 python tools/run_firmware_udp.py --firmware <путь-к-RC_CAR_ESP32> --gradle <путь-к-gradle.bat>

# Только реальная плата с отключёнными выходами; сначала проверить актуальный DHCP-адрес.
$env:RC_UDP_DEVICE_HOST='<IPv4-платы>'
$env:RC_UDP_DEVICE_CHIP_ID='5008d93f1fb8'
$env:RC_UDP_DEVICE_HOLD_MS='30000'
./gradlew.bat --no-daemon -PrecoveryInstall=true :app:testDebugUnitTest --tests vea.raceremote.control.FirmwareUdpDeviceTest --rerun-tasks
```

Тест физической платы по умолчанию пропущен; нужны оба явных параметра host/ID. До отправки управляющих пакетов он проверяет backend, отключение выходов и источник прошивки. Успех определяется свежим JUnit с одним непропущенным тестом и нулём ошибок, а не одним кодом возврата Gradle.

## Следующее физическое действие

Сначала снова подключить Samsung по USB: без него агент не может проверить новую прошивку через экран и Wi-Fi телефона. Ранее проверенные настройки телефона сохранены; расширять сроки свежести ради прохода теста не требуется.

Нужна проверка конкретного экземпляра питания и проводов перед первым SG90. Для неё нужны читаемые фотографии обеих сторон Waveshare и разъёма серво с проводами; SKU серво уже известен и повторно не запрашивается. Подключение силового питания, измерение выходного напряжения и калибровку механики агент физически выполнить не может. До согласованного подключения выходы остаются отключёнными.

По [документации Waveshare](https://www.waveshare.com/wiki/DC5-36-TO-DC3V3-5), режим5В требует вход6–36В; обычный USB5В на входе этого buck не подтверждает регулируемый выход5В. Режим задаётся перепайкой резистора0Ом, не программой. Нельзя считать модуль переключённым по его названию или фото каталога. Реальные5В надо измерить на VOUT/GND до соединения с серво. Предыдущие CAD-трассы не подтверждают распиновку/качество пайки данного образца или готовность батарейной защиты.

Камера, силовой мотор, напряжения/токи питания, калибровка SG90, дальность и FPV в этой проверке не квалифицированы. Печать по-прежнему отложена. Резервные flash-образы могут содержать Wi-Fi-реквизиты и остаются вне Git в `D:/RaceRemote-device-backups/xiao-b81f3fd90850/`; исходный app0 сохранён для отката. Временный игнорируемый Wi-Fi-заголовок использовал сохранённый профиль Windows без вывода пароля и затем удалён.
