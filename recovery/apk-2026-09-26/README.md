# Восстановление RaceRemote из APK

25 октября 2026. Из APK приложения и test APK, снятых с Samsung, извлечён собственный код RaceRemote. **Это сохранённое Java-представление байткода и материал для восстановления Kotlin, не готовая пересобранная версия приложения.**

Продолжение: сетевой код переведён обратно в Kotlin и включён в собираемый проект. Результаты и границы проверки находятся в [отчёте восстановления исходников](../../docs/apk-source-restoration.md). Архив ниже остаётся исходным материалом декомпиляции.

## Что сохранено

- [sources.zip](sources.zip): 172 Java-файла приложения и 27 test APK; метаданные указывают на 72 и 11 исходных имён Kotlin-файлов. Также включены два декодированных AndroidManifest и 18 файлов в режиме FALLBACK — всего 219 записей.
- [manifest.json](manifest.json): SHA256 исходных APK, каждой записи архива и читаемых представлений, версии инструментов и перечень пропусков.
- [readable/app/vea/raceremote/control](readable/app/vea/raceremote/control): UDP-кодек, сессия, сетевой клиент, HTTP-проверка, выбор транспорта и discovery. В этих представлениях убраны Metadata-аннотации и подставлены исходные значения LiveLiterals; строки и комментарии при подстановке не изменялись. Обновления Live Edit, не записанные в APK, этим не восстанавливаются.
- [readable/tests/vea/raceremote](readable/tests/vea/raceremote): в том числе ControlEndpointProbeTest, UDP-стенд и тест экрана.
- [protocol.md](protocol.md): извлечённые формат пакета и правила клиента.

Сторонние Java-классы из APK не экспортировались. APK и инструменты декомпиляции в Git не включены. Исходные APK находятся в `D:/RaceRemote-device-backups/samsung-RF8M811X8FK/2026-09-26/`; приложение на телефоне не заменялось.

## Пределы восстановления

JADX1.5.6 завершил обычную декомпиляцию с 16 ошибками для приложения и двумя для test APK. В пяти методах осталась явная заглушка `Method not decompiled`: основной Compose-экран, корутина DrivingPad, функция ComposeUtils, старый DriveDeviceBenchTest и UdpDiscoveryDeviceTest. Для соответствующих классов сохранены FALLBACK-инструкции; дополнительно таким же способом сохранены критические сетевые классы. FALLBACK-проходы завершились без ошибок, но это не проверка эквивалентности Java исходному байткоду.

Есть и другие предупреждения JADX о восстановлении типов/управления потоком; они сохранены в архивных исходниках. Kotlin synthetic-методы, корутины и Compose могут выглядеть как некорректный Java. Не следует копировать весь каталог в production и считать его компилируемым. Точные авторские Kotlin-файлы, комментарии, Gradle-конфигурация и история Git автоматически не восстановлены. Сборка приложения и исполнение восстановленного Java не проводились.

## Найденная причина ошибки подключения

[ControlEndpointProbe](readable/app/vea/raceremote/control/ControlEndpointProbe.java) требует HTTP200, protocol1, acceptingControl=true и поля:

```json
{
  "protocol": 1,
  "acceptingControl": true,
  "controlTransport": "udp-v1",
  "controlPort": 3334,
  "chipId": "5008d93f1fb8"
}
```

В загруженном ранее старом a8c25f6-стенде трёх последних полей не было. Первый отсутствующий ключ — controlTransport — объясняет JSONException установленного приложения. Ручной адрес не отключает эту проверку. Восстановленный ControlEndpointProbeTest содержит такой JSON-образец и проверки отказа на redirect, слишком большом теле, запрете управления и пустом объекте.

## Исходная прошивка XIAO тоже сохранилась

При сопоставлении APK обнаружено: **полная flash-копия, сделанная до загрузки старого стенда, уже содержит UDP-прошивку с нужными HTTP-полями.** Ранее агент загрузил старый стенд, не проверив исходную flash; именно это создало несовпадение с установленным APK. Предыдущие неуспешные RF-прогоны относятся к старому WebSocket-стенду, не к этой исходной UDP-прошивке.

Из app0 по 0x10000 извлечён образ 826208 байт. Контрольная сумма и встроенный SHA256 образа проверены самостоятельно и esptool. SHA256 файла — `6605db3054c823e6c1be2b5c62d9cd90b5471d442fd5b102a8f6e122f38b4126`. Локальная копия: `D:/RaceRemote-device-backups/xiao-b81f3fd90850/original-app0-2026-10-25.bin`. Образ и полная flash не публикуются: они могут содержать сетевые реквизиты. Это восстановление бинарника, не исходников C++.

Исходное приложение записано обратно только в область app0; загрузчик, таблица разделов и NVS в этом действии не восстанавливались. esptool подтвердил запись. Serial: `READY protocol=udp-v1 car=RaceRemote-5008d9 ip=192.168.1.122 udp=3334 backend=null`. Адрес относится к этому DHCP-сеансу, не является постоянным.

HTTP с ПК подтвердил outputsEnabled=false, actuatorMode=disabled и нужный контракт. С ПК прошли OPEN/HELLO, ARM/ACK, DRIVE/ACK, STOP с нейтралью; отдельная проверка молчания без предварительного STOP завершилась невооружённым нулевым планом. [Доказательства](../../docs/evidence/apk-recovery-2026-10-25/summary.json). Это проверка взаимодействия по извлечённому формату, не доказательство полного совпадения исходников, устойчивости связи с Samsung или физической остановки. Samsung в этот момент через ADB не подключён; его APK не переустанавливались. Привод не испытывался.

## Повторение и проверка

Проверка сохранённого пакета, без APK и без сети:

```powershell
uv run --no-project python recovery/apk-2026-09-26/package_recovery.py --check
```

Для повторной декомпиляции нужен [официальный JADX1.5.6](https://github.com/skylot/jadx/releases/tag/v1.5.6), ZIP SHA256 `545ea2be9c242511bc145755cf4bda2485ade42966e096f8b4d3da2a230e8974`, и Java11+. Запуск из корня репозитория:

```powershell
java -cp "<JADX>/lib/*" recovery/apk-2026-09-26/Recover.java "<APK>" "<output>"
```

Recover.java также принимает список полных имён классов через запятую и четвёртым аргументом `FALLBACK`. Точный состав fallback-файлов записан в manifest.json. После формирования рабочих каталогов app/tests/fallback-app/fallback-tests пакет создаётся package_recovery.py с путём к их общему родителю. Он проверяет ожидаемый состав, хеши, покрытие явных пропусков и содержит самопроверку подстановки констант. Это проверка целостности материалов, не сборка Android.
